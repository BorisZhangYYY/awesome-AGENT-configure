# OpenClaw Cron Template Parameter Guide

> This document describes every parameter supported by the OpenClaw cron templates in `awesome-AGENT-configure`, plus recommended configurations for different task types.

---

## 1. Core Concepts

### 1.1 Official Parameters vs Non-official Extensions

| Type | Source | How it is passed |
|------|--------|------------------|
| Official parameter | Native OpenClaw CLI parameter | Rendered as a `--xxx` flag on `openclaw cron create` |
| Non-official extension | Abstraction this template adds for Harness/Loop | Rendered into the Prompt in `--message`, executed by the Agent |

### 1.2 Template Rendering Flow

```
Scene YAML + shared template ──▶ build-cron.py ──▶ openclaw cron create --message "..." --xxx ...
```

### 1.3 Naming Convention

Cron tasks normalized by awesome-AGENT-configure (AAC) must follow this name format:

```
【AAC-Category】Task name
```

Examples:
- `【AAC-Reminder】Morning`
- `【AAC-Check】Disk space`
- `【AAC-Project】Complete login feature`

**Why enforce the naming?**

- Identify at a glance which tasks were created under AAC conventions
- The `edit-cron` / `update-cron` skills can use the `【AAC-` prefix to quickly find editable/syncable tasks
- `migrate-cron` renames tasks to the AAC format during migration
- Avoid confusion between user-created tasks and AAC tasks

The four categories map to:

| Category | Prefix | Example |
|----------|--------|---------|
| Reminder | `【AAC-Reminder】` | `【AAC-Reminder】Morning` |
| Check | `【AAC-Check】` | `【AAC-Check】Disk space` |
| Project | `【AAC-Project】` | `【AAC-Project】Login feature` |
| Learning | `【AAC-Learn】` | `【AAC-Learn】RAG research` |

Chinese templates use the localized category words `【AAC-提醒】` / `【AAC-巡检】` / `【AAC-项目】` / `【AAC-学习】`. The skill only identifies tasks by the `【AAC-` prefix.

### 1.4 Template Types

| Template | Path | Suitable for | Core mechanism |
|----------|------|--------------|----------------|
| **Shared parent template** | `OpenClaw/{zh_CN\|en_US}/cron-template/template-cron.yaml` | Reminders, checks, learning, projects | Harness (time window + deduplication) + optional Loop (state-driven + milestones) |

> **Key difference**: `template-cron.yaml` is the shared parent template for every scene. When `LOOP_MODE_ENABLED` is `true`, it enters Loop mode, which supports state resumption, goals/milestones, and auto-disabling the cron task when the goal is reached.

## 2. Official Parameters

### 2.1 Basic Information

| YAML field | CLI parameter | Description | Recommended value |
|------------|---------------|-------------|-------------------|
| `name` | `--name` | Task name | `【Category】Task name` |
| `message` | `--message` | Prompt in Agent mode | Generated by rendering `template` |
| `systemEvent` | `--system-event` | System event in main mode | Use when a silent trigger is needed |

### 2.2 Schedule Configuration

| YAML field | CLI parameter | Description | Example |
|------------|---------------|-------------|---------|
| `schedule.type` | Positional argument type | `at` / `every` / `cron` | `cron` |
| `schedule.expr` | Positional argument | Cron expression / interval / relative time | `0 8 * * *` |
| `schedule.timezone` | `--tz` | Timezone | `Asia/Shanghai` |

### 2.3 Delivery Configuration

| YAML field | CLI parameter | Description | Recommended value |
|------------|---------------|-------------|-------------------|
| `delivery.mode` | `--announce` / `--webhook` / none | Delivery mode | `announce` for reminders, `none` for checks |
| `delivery.channel` | `--channel` | Target platform | `telegram` / `slack` / `discord` |
| `delivery.to` | `--to` | Recipient target | Group/channel ID |
| `delivery.threadId` | `--thread-id` | Telegram topic ID | Forum topic ID |
| `delivery.webhookUrl` | `--webhook` | Webhook URL | Required in webhook mode |
| `delivery.bestEffort` | `--best-effort-deliver` / `--no-best-effort-deliver` | Whether delivery failure fails the task | `true` for reminders |
| `delivery.accountId` | `--account` | Multi-channel account selection | Required on multi-account platforms |

**delivery.mode:**

- `announce`: if the Agent sends nothing, the Runner delivers as a fallback. Suitable for reminders that must arrive.
- `webhook`: POST to a URL. Suitable for integrating external systems.
- `none`: no Runner fallback. Suitable for checks (silent when healthy).

### 2.4 Session Configuration

| YAML field | CLI parameter | Description | Recommended value |
|------------|---------------|-------------|-------------------|
| `session.target` | `--session` | Execution session | `isolated` for most tasks |
| `session.persistentId` | `--session` | Persistent named session ID | Use `session:xxx` when history must accumulate |
| `session.sessionKey` | `--session-key` | Session routing key | Pair with a named session |
| `session.timeoutSeconds` | `--timeout-seconds` | Timeout | 120s for reminders, 4h for development |

**Choosing session.target:**

- `isolated`: separate session; does not pollute the main session. **Recommended for most tasks.**
- `main`: main session; suitable for reminders that should interrupt the user immediately.
- `current`: current session; suitable for context-aware loop tasks.
- `session:<id>`: persistent named session; suitable for flows that need accumulated history.

### 2.5 Agent Configuration

| YAML field | CLI parameter | Description | Recommended value |
|------------|---------------|-------------|-------------------|
| `agent.agentId` | `--agent` | Bind a specific agent | **Default `main`** (see below) |
| `agent.model` | `--model` | Model override | Choose by task complexity |
| `agent.fallbacks` | `--fallbacks` | Model fallback chain | Try in order when the primary model is unavailable |
| `agent.expectFinal` | `--expect-final` | Wait for the Agent's final reply before marking complete | `true` for development/learning |
| `agent.thinking` | `--thinking` | Thinking level | `off` for reminders, `medium/high` for development |
| `agent.tools` | `--tools` | Restrict the tools available to the task | Limit per task needs |

**⚠️ agentId must be bound explicitly (incident fix from 2026-09-28):**

In multi-Agent environments (e.g. `main` + `nangongwan`), cron tasks without an agent fail trigger evaluation with
`AGENT_SELECTION_REQUIRED` ("Multiple agents are configured,
but this operation has no explicit owner"), and **the task never fires**.
`build-cron.py`'s `DEFAULTS` already sets `AGENT_ID` to `"main"`, so rendered commands always carry
`--agent main`; only override `AGENT_ID` in scene YAML when a non-main Agent is needed.

**thinking recommendations:**

- `off`: greetings, reminders, fixed-format output
- `low`: simple checks
- `medium`: development, learning
- `high`: complex analysis, code review

**tools recommendations:**

- Reminders: `exec,read` (time-window check, deduplication check)
- Checks: `exec,read,write` (run scripts, read logs, write reports)
- Development: `exec,read,write,edit,bash` (full toolset)

### 2.6 Command Mode

| YAML field | CLI parameter | Description | Example |
|------------|---------------|-------------|---------|
| `command.script` | `--command` | Script to run | `scripts/check-disk.sh` |
| `command.cwd` | `--command-cwd` | Working directory | `/srv/app` |
| `command.argv` | `--command-argv` | Exact argument array (avoids shell escaping) | `["node","scripts/export.mjs"]` |
| `command.input` | `--command-input` | Standard input | JSON string |
| `command.env` | `--command-env` | Environment variables | `KEY=VALUE` |
| `command.noOutputTimeoutSeconds` | `--no-output-timeout-seconds` | No-output timeout | `30` |
| `command.outputMaxBytes` | `--output-max-bytes` | Output limit | `65536` |

**When to use command mode:**

- Pure-script checks
- Data exports
- Deterministic tasks that need no Agent reasoning

### 2.7 Context Configuration

| YAML field | CLI parameter | Description | Recommended value |
|------------|---------------|-------------|-------------------|
| `context.lightContext` | `--light-context` / `--no-light-context` | Whether to skip workspace bootstrap | `true` for checks/reminders, `false` for development/organization |

**What `lightContext` means:**
- `true` (`--light-context`): **does not load** AGENTS.md/SOUL.md/IDENTITY.md and other system files, saving tokens. Suitable for simple reminders and checks that do not need system files.
- `false` (`--no-light-context`): **fully loads** all bootstrap files. Review/organization/development tasks must set `false` because they need the content of those files.

### 2.8 Advanced Options

| YAML field | CLI parameter | Description | Recommended value |
|------------|---------------|-------------|-------------------|
| `advanced.disabled` | `--disabled` | Create disabled by default | Use for debugging |
| `advanced.deleteAfterRun` | `--delete-after-run` | Delete after success | One-off tasks |
| `advanced.keepAfterRun` | `--keep-after-run` | Keep after success | Default |
| `advanced.wake` | `--wake` | Run immediately or wait for the next heartbeat | `now` / `next-heartbeat` |
| `advanced.exact` | `--exact` | Disable automatic stagger | `true` for reminders |
| `advanced.stagger` | `--stagger` | Explicit stagger window | `30s` |
| `advanced.pacingMin` | `--pacing-min` | Dynamic pacing lower bound | Adaptive polling tasks |
| `advanced.pacingMax` | `--pacing-max` | Dynamic pacing upper bound | Adaptive polling tasks |

**Basic information parameters** (beyond `--name`, also rendered by build-cron.py):

| Variable | CLI parameter | Description |
|----------|---------------|-------------|
| `JOB_NAME` | `--name` | Task name (must carry the `【AAC-` prefix) |
| `DESCRIPTION` | `--description` | Task description, visible in cron list |
| `DISPLAY_NAME` | `--display-name` | Human-readable UI label |
| `DECLARATION_KEY` | `--declaration-key` | Idempotent declaration key, prevents duplicates |

## 3. Non-official Extensions

These fields do not become `--xxx` flags; they are rendered into `message` and executed by the Agent at runtime.

### 3.1 Time Window `timeWindow`

| Field | Description | Default |
|-------|-------------|---------|
| `enabled` | Whether enabled | `true` |
| `start` | Window start time | Scene-defined |
| `end` | Window end time | Scene-defined |
| `action` | Behavior outside the window | `NO_REPLY` |

**Why:** Prevent OpenClaw from replaying missed tasks after a gateway restart and running them outside the intended window (startup pile-up).

### 3.2 Deduplication `deduplication`

| Field | Description | Default |
|-------|-------------|---------|
| `enabled` | Whether enabled | `true` |
| `stateFile` | State file path | `{{WORKSPACE}}/.state/reminder-xxx.txt` |

**Why:** Prevent the same task from running repeatedly during startup pile-up.

### 3.3 Persona `persona`

| Field | Description | Default |
|-------|-------------|---------|
| `mode` | `inline` / `file` | `inline` |
| `file` | External persona file path | Empty |
| `role` | Role description in inline mode | Scene-defined |

The `LOCALE` variable controls the language of the generated persona prompt: `zh_CN` (default) | `en_US`. English scenes must explicitly set `LOCALE: "en_US"`.

### 3.4 Template `template`

The template source for the entire Prompt. Scene variables replace the `{{XXX}}` placeholders in it.

**Scene-level template overrides are forbidden**

To ensure non-official Harness mechanisms such as time windows and deduplication apply consistently to every scene, **scene YAML must not define a top-level `template` field**. Every scene prompt is based on the shared `template` in `template-cron.yaml`.

Scene-specific content must be injected through the `{{SCENE_SPECIFIC_INSTRUCTIONS}}` placeholder, supplied by the scene YAML's `SCENE_SPECIFIC_INSTRUCTIONS` variable. For example, `reminders/morning.yaml`:

```yaml
variables:
  SCENE_SPECIFIC_INSTRUCTIONS: |
    You are responsible for giving the user a morning greeting at the appropriate time.
    ...
```

> ⚠️ If a scene YAML defines a top-level `template` field, `build-cron.py` reports an error.

**Mechanisms already included in the shared `template`**

- `{{PERSONA_PROMPT}}`: persona injection
- Time-window check (based on `TIME_WINDOW_ENABLED` / `WINDOW_START` / `WINDOW_END` / `WINDOW_OUT_ACTION`)
- Daily/per-run deduplication (based on `DEDUP_ENABLED` / `DEDUP_STATE_FILE`; the date is obtained by the Agent at runtime via `exec date`)
- Deduplication state write after execution (based on `DEDUP_ENABLED` / `DEDUP_STATE_FILE`; the date is obtained by the Agent at runtime via `exec date`)

## 4. `openclaw cron edit` Support Matrix

The official OpenClaw CLI has **no `cron update` subcommand**. To update an existing task, use:

```bash
openclaw cron edit <job-id> [options]
```

`edit` has patch semantics: only the specified fields change, unspecified fields stay as they are, and **the job ID does not change**.

### 4.1 Common `edit` Options and Template Variables

| Template variable | `edit` option | Description |
|-------------------|---------------|-------------|
| `JOB_NAME` | `--name` | Change the task name |
| `SCHEDULE_EXPR` (cron type) | `--cron` | Change the cron expression |
| `TIMEZONE` | `--tz` | Change the timezone |
| `MESSAGE` | `--message` | Change the Agent-mode prompt |
| `SYSTEM_EVENT` | `--system-event` | Change the systemEvent payload |
| `SESSION_TARGET` | `--session` | Change the session target |
| `MODEL` | `--model` | Change the model override |
| `THINKING` | `--thinking` | Change the thinking level |
| `TOOLS` | `--tools` | Change the tool allowlist |
| `DELIVERY_MODE: announce` | `--announce` | Enable Runner fallback delivery |
| `DELIVERY_MODE: none` | `--no-deliver` | Disable Runner fallback delivery |
| `BEST_EFFORT: true` | `--best-effort-deliver` | Delivery failure does not fail the task |
| `BEST_EFFORT: false` | `--no-best-effort-deliver` | Delivery failure fails the task |
| `LIGHT_CONTEXT: true` | `--light-context` | Lightweight bootstrap |
| `LIGHT_CONTEXT: false` | `--no-light-context` | Full bootstrap |
| `EXACT: true` | `--exact` | Disable stagger |
| `TIMEOUT_SECONDS` | `--timeout-seconds` | Agent task timeout |
| `CHANNEL` | `--channel` | Delivery channel |
| `TO` | `--to` | Delivery target |
| `STAGGER` | `--stagger` | Explicit stagger window |

### 4.2 When `edit` Cannot Be Used Directly

According to the official CLI help (`openclaw cron edit --help`), `edit` currently **does not support** command-mode fields such as `--command`, `--command-argv`, and `--command-cwd`. Therefore:

- **Agent-mode tasks**: prefer `openclaw cron edit`, which keeps the job ID.
- **Command-mode tasks**: you must `openclaw cron rm <id>` first and then `openclaw cron create ...`; the job ID changes.

### 4.3 `edit` Example

```bash
# Change the message and cron expression; the job ID does not change
openclaw cron edit abc123 \
  --message "New prompt" \
  --cron "0 7 * * *" \
  --tz Asia/Shanghai
```

## 5. Separating Project Paths from Runtime Paths

This project keeps "source/templates" and "runtime configuration" fully separate:

- **Project source** (templates, scripts, skill docs) lives in the version-controlled repository at a location chosen by the user, e.g. `/mnt/d/Study_Project/awesome-AGENT-configure`.
- **Runtime configuration** (generated scene YAML, state files) goes into the OpenClaw workspace: `~/.openclaw/workspace/awesome-AGENT-configure/cron/`.

The skill therefore distinguishes two paths:

| Variable | Meaning | Example |
|----------|---------|---------|
| `AAC_REPO` | Project repository root | `/mnt/d/Study_Project/awesome-AGENT-configure` |
| `AAC_WORKSPACE` | Runtime configuration root | `~/.openclaw/workspace/awesome-AGENT-configure` |

### 5.1 Locating the Project Repository (`AAC_REPO`)

No skill uses the `/path/to/awesome-AGENT-configure` placeholder anymore. Before running steps that use project scripts, the AGENT should locate the project root and save it to `AAC_REPO`.

```bash
export AAC_REPO=$(python3 - <<'PY'
import os, sys

def locate_repo():
    # 1. AAC_REPO environment variable (explicitly set by the user, e.g. /mnt/d/Study_Project/awesome-AGENT-configure)
    env = os.environ.get("AAC_REPO")
    if env and os.path.isfile(os.path.join(env, "OpenClaw/skills/aac-cron-manage/scripts/build-cron.py")):
        return env
    # 2. Current working directory
    cwd = os.getcwd()
    if os.path.isfile(os.path.join(cwd, "OpenClaw/skills/aac-cron-manage/scripts/build-cron.py")):
        return cwd
    # 3. Bounded-depth search under $HOME
    home = os.path.expanduser("~")
    for root, dirs, _ in os.walk(home):
        if "awesome-AGENT-configure" in dirs:
            p = os.path.join(root, "awesome-AGENT-configure")
            if os.path.isfile(os.path.join(p, "OpenClaw/skills/aac-cron-manage/scripts/build-cron.py")):
                return p
        if root.count(os.sep) - home.count(os.sep) >= 4:
            del dirs[:]
    return ""

path = locate_repo()
if not path:
    print("ERROR: awesome-AGENT-configure not found; set the AAC_REPO environment variable first", file=sys.stderr)
    sys.exit(1)
print(path)
PY
)
```

Locating priority:

1. The `AAC_REPO` environment variable.
2. The current working directory (if it is the project root).
3. A directory named `awesome-AGENT-configure` within the first 4 levels under `$HOME` that contains `OpenClaw/skills/aac-cron-manage/scripts/build-cron.py`.

### 5.2 Runtime Path (`AAC_WORKSPACE`)

Runtime-generated YAML and state files live in the OpenClaw workspace, separate from project source:

```bash
AAC_WORKSPACE="${AAC_WORKSPACE:-$HOME/.openclaw/workspace/awesome-AGENT-configure}"
mkdir -p "$AAC_WORKSPACE/cron"
```

### 5.3 Usage

```bash
# Render the create command
python3 "$AAC_REPO/OpenClaw/skills/aac-cron-manage/scripts/build-cron.py" \
  "$AAC_WORKSPACE/cron/init-<job-name>/init-<job-name>.yaml"
```

If locating `AAC_REPO` fails, stop and ask the user to set the `AAC_REPO` environment variable.

## 6. Development Iteration Template (Loop Method)

### 6.1 What the Loop Method Is

The Loop method is a **state-driven incremental development model**. Core ideas:

1. **State resumption**: record progress in `.state/session.json` to stay continuous across sessions
2. **Checklist-driven**: a START checklist (on startup) and an EXIT checklist (on exit) ensure quality every session
3. **Incremental iteration**: do a small piece each time, accumulating into a complete feature
4. **Automatic recovery**: use the state to decide whether to "claim a new task", "resume", or "unblock"

### 6.2 Differences from the Generic Cron Template

| Dimension | Generic Cron (reminders/checks) | Development iteration (Loop) |
|-----------|---------------------------------|------------------------------|
| **Execution mode** | Single run; done when it ends | Iterative; state resumes |
| **State management** | None (or simple deduplication) | Yes (a full state machine in session.json) |
| **Checklist mechanism** | None | START / EXIT checklists |
| **Timeout** | Short (2-5 minutes) | Long (2-4 hours) |
| **lightContext** | Usually `true` | Must be `false` (needs system files) |
| **thinking** | Usually `off` | Usually `medium/high` |
| **Daily deduplication** | Usually enabled | Usually disabled (multiple iterations per day) |

### 6.3 State Machine

```
+--------+     claim new task     +-------------+
| ready  | ---------------------> | in_progress |
+--------+                        +-------------+
       ^                                 | complete / partially complete
       |                                 v
       +--------------------------+  blocked
       |                          +---------+
       |                          | blocked | ——→ resolve within time limit (≤15min)
       |                          +---------+      keep blocked on timeout
```

### 6.4 The Three Phases of Development Iteration

#### PHASE 1: START — session startup

**Must do**:
1. Read the state file (`session.json`)
2. Read the project TODO.md
3. Read recent git commit history
4. Determine the session type (ready / in_progress / blocked)
5. Load development context (code, tests, docs)

#### PHASE 2: DEV — execute the development task

**Core development work**:
1. Implement code for the current task
2. Follow the minimal-change principle and the verification loop
3. Run tests to verify

#### PHASE 3: EXIT — session exit

**Must do**:
1. Code wrap-up (syntax check, tests, git diff)
2. Security review (no API keys, no private paths)
3. Git commit (**do not push**; follow the safety red lines)
4. Update the state file (status, next_step, tech_debt)
5. Update TODO.md
6. Report (if delivery is configured)

### 6.5 Project Scene File Examples

#### Feature development (`projects/feature.yaml`)

```yaml
templateRef: "../../template-cron.yaml"

variables:
  # Enable Loop mode
  LOOP_MODE_ENABLED: "true"

  JOB_NAME: "【AAC-Project】XXX feature development"
  SCHEDULE_EXPR: "0 10 * * 1-5"  # Weekdays at 10:00
  TIMEZONE: "Asia/Shanghai"
  WINDOW_START: "09:00"
  WINDOW_END: "12:00"

  DEV_PROJECT_NAME: "MyProject"
  DEV_PROJECT_DIR: "/path/to/project"
  DEV_PHASE: "Phase 1"
  DEV_BRANCH: "dev/main"
  DEV_STATE_FILE: "{{DEV_PROJECT_DIR}}/.state/dev-session.json"
  DEV_TEST_PATTERN: "test_*.py"
  # Git commit prefix (common: feat/fix/refactor/maint/docs/test/chore)
  DEV_COMMIT_PREFIX: "feat"
  # Project docs directory
  DEV_DOCS_DIR: "{{DEV_PROJECT_DIR}}/docs"

  # Goal and milestones
  DEV_GOAL: "Complete the development and testing of XXX"
  DEV_MILESTONES: '["Milestone 1: Base module", "Milestone 2: Core logic", "Milestone 3: Integration testing and documentation"]'
  DEV_CURRENT_MILESTONE: "Milestone 1: Base module"
  DEV_AUTO_DISABLE_ON_GOAL_REACHED: "true"

  # Core: define the concrete development instructions
  DEV_TASK_INSTRUCTIONS: |
    ### Current task: implement XXX

    Steps:
    1. ...
    2. ...
    3. ...

    Acceptance criteria:
    - All tests pass
    - Code follows project conventions

  # Project-type configuration
  LIGHT_CONTEXT: "false"
  THINKING: "medium"
  TOOLS: "exec,read,write,edit,bash"
  TIMEOUT_SECONDS: "14400"  # 4 hours
  SESSION_TARGET: "isolated"

  # Daily deduplication is usually unnecessary
  DEDUP_ENABLED: "false"
  DEDUP_STATE_FILE: "{{WORKSPACE}}/.state/dev-feature-dedup.txt"
```

  DEV_BRANCH: "main"

  DEV_COMMIT_PREFIX: "maint"
  # Project docs directory

  # Goal and milestones

| Configuration | Feature development | Maintenance session | Refactoring task |
|---------------|---------------------|---------------------|------------------|
| `SCHEDULE_EXPR` | `0 10 * * 1-5` | `0 15 * * 1-5` | `0 10 * * 1,3,5` |
| `TIMEOUT_SECONDS` | `14400` (4h) | `7200` (2h) | `10800` (3h) |
| `THINKING` | `medium` | `medium` | `high` |
| `LIGHT_CONTEXT` | `false` | `false` | `false` |
| `DEDUP_ENABLED` | `false` | `false` | `false` |
| `TOOLS` | `exec,read,write,edit` | `exec,read,write,edit` | `exec,read,write,edit` |
| `DEV_COMMIT_PREFIX` | `feat` | `maint` | `refactor` |

### 6.7 State File Format

The standard state file (`session.json`) format used by the development iteration template:

```json
{
  "status": "ready | in_progress | blocked | completed | goal_reached",
  "current_card": "Task identifier (e.g. P4-T1)",
  "last_session": "2026-06-29T10:00:00+08:00",
  "next_step": "The specific, actionable next step",
  "blockers": ["Blocker description"],
  "tech_debt": ["Debt description"],
  "test_coverage": "208/208 all passing",
  "goal": "Overall goal description",
  "milestones": ["Milestone 1", "Milestone 2", "Milestone 3"],
  "current_milestone_index": 0,
  "dev_log": [
    {
      "time": "2026-06-29T10:00:00+08:00",
      "task": "P4-T1",
      "summary": "Completed xxx",
      "tests": "passing",
      "commit": "abc1234"
    }
  ]
}
```

### 6.8 Safety Red Lines (Development Template Specific)

1. **No automatic push**: the template only runs `git commit`; `git push` requires human review.
2. **Sensitive information check**: the EXIT phase must check for API keys, tokens, and private paths.
3. **Change scope confirmation**: `git diff` to confirm no unexpected files were modified.
4. **Commit only when tests pass**: do not commit code with failing tests (or mark it explicitly as WIP).
